# Site 前台站点内置模板与按文件定制实施方案

日期：2026-10-29

状态：已实现并完成本地验证，尚未部署。2026-10-29 用户批准按本方案驱动 sub agent 分批开发，代码、测试与接入文档已完成。真实邮件和支付平台仍需配置后验收。

适用版本：当前仓库 `package.json` 标识的 1.0.0 工作树。本文保留已批准的设计及实施记录，不代表生产环境已经发布；具体本地验证范围见第 12 节。

## 1. 问题与目标

实施前，用户部署 LicenKit 后只能得到 API 和管理后台。客户收到的邮件登录链接指向使用方自己的前台站点，但 LicenKit 没有提供对应页面，因此使用方还需要自行开发登录、授权查询和设备管理页面，才能完成客户侧使用流程。

Site（前台站点）指供访客了解产品、完成购买，以及供已购用户登录和管理授权的网页部分。本方案提供一套随系统部署的内置页面，并允许使用方只替换需要定制的文件：

> 每次请求先读取 `custom` 中的对应文件，只有文件不存在时才读取 `builtin` 中的同名文件。

目标是让空的 `custom` 目录也能运行完整的前台站点；用户可以逐步替换页面、样式、图片、脚本或公开配置，而不用先复制和维护整套模板。

现有客户接口已经提供邮箱登录、授权查询、设备释放、注册码重新生成和订阅管理能力。本次主要补充页面、文件选择及构建部署，不新增数据库表。

命名统一采用以下约定：

| 对象 | 统一名称 |
| --- | --- |
| 模块英文名 | Site |
| 模块中文名 | 前台站点 |
| 源码目录 | `apps/site/` |
| 内置模板与用户模板 | `builtin`、`custom` |
| 发布产物的内部目录 | `dist/__site/` |
| 面向已购用户的授权管理入口 | 我的授权 |

Customer 继续表示业务中的客户，现有 `/customer` 页面路径、Customer API 和 `customer_site_url` 等已发布接口字段沿用当前合同。模块名称统一为 Site，不把客户业务概念改成 Site，也不在文档改名时改变接口。

## 2. 目录与技术形式

在仓库中新增以下目录：

```text
apps/site/
├── builtin/
│   ├── index.html
│   ├── pricing.html
│   ├── purchase-success.html
│   ├── 404.html
│   ├── site.json
│   ├── customer/
│   │   ├── login.html
│   │   ├── auth.html
│   │   ├── index.html
│   │   └── license.html
│   └── assets/
│       ├── site.css
│       ├── theme.css
│       ├── logo.svg
│       └── …页面需要的脚本
└── custom/
```

- `builtin`：由 LicenKit 维护，随版本提供和更新。
- `custom`：由使用方维护，初始没有模板文件。Git 如需占位文件，该文件不参与发布。

模板使用普通 HTML、CSS 和浏览器 JavaScript，客户数据通过现有 API 获取。第一版不引入服务端模板引擎或模板管理系统，用户可以直接阅读和修改文件。

页面使用固定的公开资源地址，不直接引用包含 `builtin` 或 `custom` 的地址。文件实际来自哪个目录，由服务端统一选择。

## 3. 默认模板的页面范围

| 页面 | 访问路径 | 模板文件 | 默认功能 |
| --- | --- | --- | --- |
| 站点首页 | `/` | `index.html` | 展示品牌、产品简介，以及“查看价格”“我的授权”等入口 |
| 产品与价格页 | `/pricing` | `pricing.html` | 展示配置的产品和购买方案，通过 Paddle 打开结账窗口 |
| 购买结果页 | `/purchase-success` | `purchase-success.html` | 展示结账后的提示，引导查看邮件或进入“我的授权” |
| 邮箱登录页 | `/customer/login` | `customer/login.html` | 输入购买邮箱，完成人机验证，申请邮件登录链接 |
| 邮件登录确认页 | `/customer/auth` | `customer/auth.html` | 接收邮件中的一次性登录凭证，点击“确认登录”后完成登录 |
| 我的授权 | `/customer/` | `customer/index.html` | 展示当前用户的产品授权、状态、有效期和详情入口，支持退出登录 |
| 授权详情 | `/customer/licenses/:licenseId` | `customer/license.html` | 展示指定授权的内容、设备、订阅及可用管理操作 |
| 页面不存在 | 未匹配的页面地址 | `404.html` | 返回 HTTP 404，提供返回首页和授权列表的入口 |

授权详情路径中的 `licenseId` 是当前查看的授权编号，只用于请求授权接口，不直接拼接为模板文件路径。

### 3.1 授权详情中的操作

设备、注册码和订阅管理统一放在授权详情中，不额外拆分页面。

| 操作 | 用户看到的行为与影响 |
| --- | --- |
| 设备管理 | 查看已激活设备，释放设备占用 |
| 重新获取注册码 | 生成新注册码，旧码失效，已激活设备保留 |
| 安全重置 | 生成新注册码，旧码失效，同时撤销现有设备激活 |
| 订阅管理 | 展示续费情况；由支付平台管理的订阅，提供跳转支付平台的入口 |

可用操作依据接口返回的状态展示，实际权限和是否允许执行仍由服务端判断。

新注册码在操作成功后当次展示并允许复制，不写入浏览器存储。邮件发送出现问题时，仍展示已经成功生成的新注册码，分别说明操作结果和邮件状态。邮件服务商接受请求不能表述为“邮件已送达”。

### 3.2 购买流程

产品及购买方案来自站点公开配置。购买按钮直接使用 Paddle 的浏览器脚本打开结账窗口，不新增公开商品查询或结账 API。

购买结果页只反馈结账流程，不能仅凭浏览器回调或访问结果页就宣称“付款成功”或“授权已发放”。实际授权以服务端验证并处理支付通知后的结果为准。

默认不放虚构商品和有效购买按钮。尚未配置商品时，价格页展示暂无在售产品，已购用户仍可进入授权管理。

### 3.3 页面体验

默认页面采用简洁、便于替换品牌的布局，适配桌面和手机，提供简体中文和英文。文案使用“我的授权”“已激活设备”“管理订阅”等用户能够理解的说法。

加载、空列表、请求失败和操作结果均提供明确状态；键盘操作、焦点提示和表单标签随页面一起验收。

## 4. 公开配置与品牌定制

站点公开配置集中保存在 `site.json`，配置范围如下：

| 配置内容 | 用途 |
| --- | --- |
| 品牌名称、简介、支持链接 | 首页、导航和帮助入口 |
| API 地址 | 默认访问当前站点的 `/api/v1`，也支持填写现有 API 地址 |
| 产品与购买方案 | 展示名称、说明、价格文字和 Paddle Price ID |
| Paddle 环境与前端公开 Token | 打开对应环境的结账窗口 |

`site.json` 属于浏览器可读取的公开文件。支付平台密钥、邮件服务密钥及其他服务端凭据不能写入该文件或其他模板资源。

`site.json` 遵守整文件覆盖：存在 `custom/site.json` 时完整使用该文件，不逐字段合并。用户可从内置配置复制一份后修改。

样式定制分为两个用途：

- `assets/site.css` 提供基础布局和默认颜色。
- `assets/theme.css` 在基础样式之后加载，内置文件初始为空，供用户覆盖颜色、字体、圆角等样式。

用户只需要调整品牌外观时，可以只添加 `custom/assets/theme.css`；只需要替换标志时，可以只添加 `custom/assets/logo.svg`。

## 5. custom 按文件覆盖规则

### 5.1 请求选择流程

每个 Site 页面或资源请求按以下顺序处理：

1. 校验并规范化请求路径，将其映射为一个明确的相对文件路径。
2. 读取 `custom` 下的该文件。
3. 只有该文件不存在时，才读取 `builtin` 下的同名文件。
4. 两边都不存在，返回 HTTP 404。
5. 文件存在但读取或处理失败时，报告该错误，不切换版本。

选择规则可表示为以下伪代码，正式实现还需要处理请求方法、路径校验、响应头和错误记录：

```text
filePath = mapRequestToFile(request)

customResponse = readAsset("custom/" + filePath)
if customResponse.status != 404:
    return customResponse

builtinResponse = readAsset("builtin/" + filePath)
if builtinResponse.status != 404:
    return builtinResponse

return notFoundResponse(request)
```

HTTP 404 在这里仅表示静态资源接口确认文件不存在。异常、HTTP 500 等其他结果不能当作文件不存在处理。

### 5.2 覆盖示例

| 请求 | custom 内容 | 实际使用 |
| --- | --- | --- |
| `/customer/login` | 存在 `customer/login.html` | 用户定制的登录页 |
| `/customer/` | 没有 `customer/index.html` | 内置授权列表 |
| `/assets/logo.svg` | 存在 `assets/logo.svg` | 用户自己的图片 |
| `/assets/site.css` | 没有 `assets/site.css` | 内置基础样式 |

页面和它引用的资源分别选择。例如，自定义登录页仍然可以引用内置样式和登录脚本；只替换一张图片，不需要复制整套页面。

所有页面引用统一公开地址，例如 `/assets/site.css`。公开 URL 不因文件来自 `builtin` 还是 `custom` 而改变。

覆盖按相对路径和文件名匹配，区分大小写。空文件也算存在，不因为内容为空而读取内置版本。删除自定义文件并重新部署后，该位置恢复使用内置文件。

### 5.3 新增页面

除覆盖默认页面外，用户可以在 `custom` 中新增公开页面和资源：

```text
custom/about.html        → /about
custom/help/index.html   → /help/
custom/assets/banner.svg → /assets/banner.svg
```

默认页面采用第 3 节列出的固定映射。新增普通页面按照文件规则映射：无扩展名的页面路径对应同名 `.html`，以 `/` 结尾的目录路径对应该目录下的 `index.html`，带资源扩展名的路径按文件读取。

页面请求不存在时，按相同覆盖规则选择 `404.html`，响应状态保持 404。缺失的脚本、样式或图片直接返回资源不存在结果，不替换成 HTML 首页或 404 页面内容。

### 5.4 路径边界

- `/admin`、`/api` 及内部打包目录属于保留路径，不进入 Site 文件选择流程。
- `custom` 不能覆盖管理后台、API 或静态资源发布控制文件。
- 路径校验拒绝目录越界和跨出模板目录的文件引用；构建不跟随越界的符号链接。
- 只发布公开页面资源，占位文件、隐藏文件和服务端凭据不参与模板发布。
- Site 资源读取仅接受 GET 和 HEAD，业务写操作仍走现有 API。
- 内部打包地址不作为公开访问入口，用户统一访问站点页面与资源的公开路径。

## 6. 构建与运行方式

### 6.1 复用现有静态资源服务

继续使用现有 Cloudflare Worker 和 `ASSETS` 静态资源接口。Worker 是当前处理 LicenKit API 的服务端程序；`ASSETS` 是读取随部署上传的页面文件的接口。

构建时将两套文件分别放入发布目录，保留来源目录，不提前合并成一套文件：

```text
dist/
├── admin/
└── __site/
    ├── builtin/
    └── custom/
```

请求到达 Worker 后，才按本方案顺序读取 `custom` 和 `builtin`。每次请求的文件选择针对当前部署版本中的文件，不依赖运行时可修改的本地磁盘。

新增一个负责 Site 请求的模块即可，不新增存储服务或模板管理系统。代价是前台页面和资源请求需要经过 Worker；没有自定义文件时，会先得到一次不存在结果，再读取内置文件。

### 6.2 静态资源配置

调整现有 `wrangler.jsonc` 的静态资源配置：

- 相关请求先经过 Worker，保证覆盖规则和保留路径检查始终执行。
- `html_handling` 使用 `none`，关闭静态资源接口自动进行的 HTML 地址改写。
- `not_found_handling` 保持 `none`，不让缺失文件自动变成首页或其他页面。

页面路径到 HTML 文件的映射由服务端显式完成。管理后台入口和现有恢复账号等页面也需要显式读取对应的 Admin 页面，避免全局 HTML 配置变化影响原有访问路径。

Cloudflare 的静态资源接口会应用上述配置，因此不能依赖默认地址改写来判断文件是否存在。相关依据：

- [Cloudflare Static Assets Configuration and Bindings](https://developers.cloudflare.com/workers/static-assets/binding/)
- [Cloudflare Static Assets HTML handling](https://developers.cloudflare.com/workers/static-assets/routing/advanced/html-handling/)

### 6.3 缓存

页面、配置和资源保持固定文件名。HTML 和公开配置要求浏览器重新验证缓存；登录相关页面及客户数据响应禁止缓存，避免更新后继续使用旧页面或残留用户信息。固定名称的脚本和样式也需要校验缓存，避免新旧版本混用。

### 6.4 开发与更新

开发环境监听 `builtin` 和 `custom` 的文件增删改，同步更新开发资源，刷新页面即可查看结果。

生产环境中的模板随版本发布。修改源文件后，需要重新构建和部署才会生效；本次不提供运行时文件上传或在线编辑入口。

构建脚本只处理发布产物，不修改 `builtin` 或 `custom` 源文件。更新 LicenKit 时只更新官方维护的文件，不用复制、同步或清理命令覆盖 `custom`。用户仍需自行备份或通过版本管理保存定制内容。

## 7. 站点入口与已有实例切换

### 7.1 新部署

根路径 `/` 从跳转管理后台改为展示站点首页。管理后台继续使用 `/admin/`，API 继续使用现有 `/api/v1` 路径。

初始化时，前台站点地址默认填写当前站点地址。内置站点第一版默认挂在域名根路径，页面调用当前站点的 API。

### 7.2 已有外部官网

保留使用方自己开发并部署前台站点的原有接入能力，不自动修改已经保存的前台站点地址。现有接口对前台站点地址、同站域名和请求来源的限制继续生效；填写其他 API 地址不能绕过这些校验。

已有外部站点使用基础路径的接口合同继续保留；本次不扩展内置页面在任意基础路径下托管的能力。

### 7.3 切换到内置站点

已有实例切换到内置站点，作为部署时的明确迁移动作处理：

1. 确认新站点地址和对应部署的文件版本。
2. 部署并确认新站点页面可访问。
3. 定点调整该实例保存的前台站点地址，沿用现有地址校验规则。
4. 重新申请邮件登录链接，验证登录、授权查询和操作流程。

不能只修改前端配置，因为邮件链接和请求来源校验也依赖服务端保存的前台站点地址。不自动改写已有实例记录，也不新增数据库表结构迁移。

## 8. 登录与客户操作规则

默认页面继续遵守现有接口合同：

1. 邮件链接中的一次性登录凭证仅从 URL Fragment，也就是 `#` 后的部分读取；读取后立即清理地址栏，只保存在当前页面内存。
2. 打开邮件链接或邮件扫描器预取页面不能消费凭证。用户点击“确认登录”后才提交消费请求。
3. 一次性凭证处理期间不加载支付、统计等第三方脚本。
4. 邮箱登录申请在服务端接受后展示一致结果，不泄露邮箱是否存在。
5. 浏览器请求携带现有会话 Cookie。用于验证写请求的 CSRF Token 只保存在当前页面内存，不写入浏览器存储。
6. 修改设备或注册码时，携带服务端要求的会话和请求验证信息。
7. 服务端要求重新验证邮箱时，引导重新登录；完成后由用户重新发起原操作，不自动重做设备释放、注册码重新生成等写操作。
8. 客户归属、授权权限和是否允许执行操作，始终由服务端决定。
9. 一次性登录凭证、新注册码和支付平台管理页面的短期跳转地址不进入日志、统计或浏览器持久存储。

## 9. 错误处理与阻塞范围

以下规则已随方案批准并实现。文件不存在时读取内置版本是明确的产品行为，不用于掩盖读取失败、脚本错误或接口异常。

| 情况 | 拟采用的处理 | 影响范围 |
| --- | --- | --- |
| custom 文件不存在 | 正常读取 builtin，不提示错误 | 不阻塞 |
| 两边都没有请求页面 | 返回 HTTP 404 | 当前页面 |
| 已选中文件读取失败 | 当前请求失败并记录诊断，不切换模板 | 当前请求 |
| 自定义脚本或配置错误 | 明确报告，不悄悄使用内置版本 | 使用该文件的页面或功能 |
| 登录验证或核心授权查询失败 | 显示原因与重试入口 | 当前登录或查询操作 |
| 订阅信息等独立区域加载失败 | 仅该区域显示错误，已加载的授权和设备信息继续可用 | 对应区域 |
| 注册码操作成功，但邮件发送异常 | 展示新注册码和邮件状态，不把整个操作显示为失败 | 邮件通知 |
| 构建发现配置格式错误、保留路径冲突或越界文件引用 | 停止本次构建，指出具体文件和原因 | 本次构建发布 |

对能够在构建阶段确认的配置错误，尽早报告；浏览器运行时才能发现的错误，在对应页面说明。错误信息保留可诊断线索，不暴露服务端凭据或敏感结果。

## 10. 实施步骤与修改范围

按以下顺序实施，每个阶段围绕可验收的结果完成：

1. 建立 `builtin` 和 `custom` 目录、构建脚本及文件选择模块，验证按文件覆盖规则。
2. 调整站点入口及静态资源配置，确认管理后台和 API 路由正常。

## 11. 验收标准

### 11.1 文件选择

- `custom` 为空时，全部内置页面可访问。
- 单独覆盖 HTML、CSS、图片、脚本及配置均生效，其他文件继续使用内置版本。
- 自定义页面可以引用内置资源。
- 自定义文件删除并更新部署后恢复内置版本。
- 空文件、读取失败和脚本错误不会被误判为文件不存在。
- 新增普通页面、目录首页及额外资源按映射规则访问。
- 未知页面及缺失资源返回正确的 HTTP 404。
- 保留路径和内部打包路径不会绕过服务端边界。

### 11.2 客户流程

- 登录链接打开、确认、刷新、过期及重复使用符合现有规则。
- 不同邮箱的登录申请不会暴露邮箱是否存在。
- 授权列表和详情仅展示当前客户可读取的数据。
- 设备释放、重新获取注册码、安全重置及订阅跳转可用，影响与文案一致。
- 需要重新登录时不自动重做写操作。
- 邮件异常不会遮蔽已经完成的操作结果。
- 购买结果页不以浏览器结果代替服务端支付与发证事实。
- 尚未配置商品时，授权管理仍可使用。

### 11.3 回归与验证方式

- 管理后台及现有 API 路由通过回归检查，特别验证 HTML 路由配置变化后的后台入口和账号恢复页面。
- 桌面、手机、键盘操作和两种语言通过浏览器验收。
- 验证重新部署后页面及脚本不会因旧缓存混用。
- 运行项目现有的类型检查、测试和构建。
- 支付页面先验证 Paddle Sandbox，不执行真实扣款。
- 涉及替代邮件服务、模拟接口或本地环境的验证，在实施结果中标明范围，不将其表述为真实邮件送达或生产支付验收。
