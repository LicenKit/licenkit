# CLA 维护说明

当前使用 [CLA v1.0](../../../CLA.md)，确认流程已启用：贡献者本人在 PR（合并请求）中评论同意，维护者在合并前人工核查并保存记录。协议、贡献指南、PR 模板和 README 随同一次仓库更新发布，无需单独发布 Release 或先发布协议再回填链接。

## 协议版本

- 贡献者阅读仓库中的 CLA，并在本人评论中明确同意 v1.0；无需勾选或填写提交编号。
- 维护者核查时保存该版本的完整协议文件、实际提交的完整 SHA（Git 提交编号）和对应永久链接。不能把仅含旧协议的提交记作 v1.0。
- 在 GitHub 文件页面按 `y` 可取得[指向具体提交的永久链接](https://docs.github.com/en/repositories/working-with-files/using-files/getting-permanent-links-to-files)。贡献指南与 PR 模板中的阅读入口可使用普通文件链接，核查记录中的链接须指向确认版本的实际提交。
- 同一版本的条款保持不变。修改条款时升版本，同步更新贡献指南、PR 模板和 README，并保留旧版本原文及确认记录。需要新版本授权的贡献须重新取得确认，不能把旧评论视作同意最新条款。

## 每个 PR 的人工核查

1. 核对贡献者本人账号发表的确认评论，明确同意 CLA v1.0 的英文条款，并授权本次 PR 中由其有权授权的贡献。标准评论为：

   > 我已阅读并同意 LicenKit CLA v1.0 的英文条款，并将本 PR 中由我有权授权的贡献按该协议授权。

2. 核对作者、共同作者和材料来源。各相关权利人分别确认自己的贡献；雇主或公司所有的部分由对应权利人或有权代表授权。维护者不代发同意评论，也不将一个人的确认视作其他人的授权。
3. 保存协议版本、本人评论、账号、时间与对应贡献记录。评论可以编辑或删除，应保存核验时的原文及可见编辑信息，不能只保存 URL。
4. 合并前复核新增作者、材料、权属或协议版本变化；需要补充授权时取得对应确认。记录不清时先澄清，再合并需要 CLA 的贡献。维护者自身的作品同样核查其实际权利来源。
5. 完成核查后，在 PR 留下一条简短接受记录，注明协议版本、确认评论链接和核查的 PR head SHA（当时的最新提交编号）。合并后补记实际合并提交。

确认只覆盖明确授权的本次 PR 贡献。其他历史贡献需要补充授权时，另列范围并取得同意。该流程依靠维护者人工核查，不提供自动状态检查。

## 记录保存

由协议中的接收方或其授权维护者核查并保管记录，使用不对外公开的目录或现有私密记录系统即可。记录用于核对贡献授权及后续权利承接，仅向负责核查与保管的人员开放，定期备份。每个 PR 保存：

- 完整协议文件、版本、实际提交编号及永久链接。
- 贡献者稳定数字账号 ID、当时用户名、本人评论链接与 ID、UTC 创建时间、可见更新时间、确认原文和核验时的 PR 正文。
- PR 编号和链接、核查时的最新提交编号、各作者授权的贡献范围，合并后补记合并提交。
- 维护者账号、UTC 核查时间及接受评论链接。

仅在需要核实权属或代表权限时，与贡献者约定私密渠道收取补充证明；有项目转让时保存书面承接文件、主体、时间和范围。完整记录和证明不提交到公开仓库或 PR，没有具体核验需要时不额外收集姓名、地址等资料。

用户名变化时通过稳定 ID 核对；账号持有人或法律主体变化时另行核查，不能仅凭 ID 相同推定主体未变。发现确认被撤回、删除或修改时记录变化，合并前授权不清则先澄清。
